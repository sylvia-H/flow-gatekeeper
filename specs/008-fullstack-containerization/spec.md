**Feature Branch**: `008-fullstack-containerization`

**Created**: 2026-07-15

**Status**: Draft

**Input**: User description: "008-fullstack-containerization"（依 `docs/Flow-Gatekeeper-SDD-完整實作指南.md` §14 方向藍圖與 `docs/adr-002-productionization-scope.md` §5 既定決策起草）

## Clarifications

### Session 2026-07-15

- Q: 全棧模式的入口拓樸——瀏覽器要面對幾個位址? → A: 單一入口——前端容器內建反向代理，只暴露一個 port，`/ws` 與 `/diagnoses` 同源轉發至 api 容器；api 不對外暴露 port。前端沿用現行同源相對路徑、原始碼零改動，故無後端位址需注入前端產物。
- Q: 模式分組的命名與 worker 歸屬? → A: 收斂為單一 `demo` 分組，三端（web/api/worker）全在其中；007 的 `supervised` 退場，README 與指南同步更名（**回補標的經 analyze 查證後校正**：指南 §13 為誤列——全檔 0 處 `supervised`，實際回補處為 §14／§16，現況見 FR-016 註）。理由：只留「不帶分組＝開發模式／`demo`＝全棧」一條心智線；單獨起 worker 以指名服務達成（分組不影響指名），故無 granularity 損失；避免並存兩個分組導致「起了前端與 Gateway 卻沒有 worker」這種畫面正常、診斷永不完成的無聲失敗。
- Q: 示範資料（seed）的就緒時機? → A: 獨立的一次性 seed 服務（init container 語意）——每次全棧啟動跑一次、完成即退出，api 以「seed 成功完成」為啟動條件。理由：現行 seed 已是破壞性重置（`deleteMany` → `insertMany`）且已隨 api 建置產出，故復用 api 映像即可、無需額外映像或 host 端工具鏈；若改綁進 api 啟動路徑，FR-003 的崩潰自動重啟會導致每次重啟都重置示範資料（與 US1 場景 3 的復原演練衝突，且讓 api 重啟路徑開始碰資料，違反 FR-014 精神）。
- Q: 容器化 api 的監督參數（重啟上限、停止寬限期）? → A: 重啟上限 5 次（沿用 007 worker 的監督語意，兩端一致）；停止寬限期 **15s**，依 api 自身收尾成本另定，不照抄 worker 的 45s（後者是為涵蓋 `AI_TIMEOUT_MS` 30s 的 LLM 收尾而算，api 不呼叫 LLM，其收尾僅為關閉連線、量級為秒內）。**前提修正**：起草時假設「api 有既有的優雅關閉流程」為誤——`bootstrap()` 未呼叫 `enableShutdownHooks()`、亦無 `SIGTERM` handler，故現有的四個 `onModuleDestroy`（Mongo／QueueEvents／AI relay／Gateway）從未被觸發，行程收到 SIGTERM 即刻死亡。因此 008 MUST 為 api 補上優雅關閉處理（對齊 007 worker 的形狀），此為 FR-014「無行為變更」的**窄範圍例外**（僅關閉路徑，不觸碰背壓／佇列／streaming／快取語意）——理由：收到 SIGTERM 即暴斃的行程稱不上「可部署的受監督形態」，該缺口屬 ADR-002 §3 的「執行模型缺席」，非打包以外之事。
- Q: 祕密缺漏（`GEMINI_API_KEY` 未填）時的處置? → A: **沿用現行語意、不新增任何祕密檢查**——查證確認空金鑰不會使 worker 啟動失敗（provider 建構子只存放金鑰、不驗證），故全棧照常啟動、遙測與背壓正常，僅 AI 診斷與快取命中失效並走既有 `ai/error` 路徑；web 既有的錯誤訊息映射已有金鑰專屬條目（「AI 服務金鑰無效或未授權」），告警機制**無需新建**。理由：曾評估另兩案並排除——(1)「由編排宣告必填」**不可行**：compose 變數插值只讀 shell 環境與根目錄 `.env`、**不讀 `env_file`**，而本專案祕密全在各 app 層 `.env`；強行採用須把祕密搬到根目錄，將推翻「不重新設計設定佈局」的假設、使根目錄 `.env.example` 的既有敘述失效，並產生兩層語意不同的 `.env`（傷及 SC-007）。(2)「一次性前置檢查服務」成本雖低（約 30 行、可復用 007 映像的第二進入點模式，無需新映像），但其**價值與代價同源**：把缺金鑰當致命錯誤，會讓「沒有 Gemini 帳號的評估者」完全看不到系統（4 個賣點 0 個可見），直接違反 US2「拿到 repo 想在最短時間內看到系統跑起來」的價值主張；而它保護的展示者恰是最會事前演練、最不需要保護的一方。沿用現行語意則讓無金鑰者仍可見 2/4 賣點（遙測、背壓）。
- Q: 「全棧就緒」的健康判定依據? → A: 以**既有對外介面**探活、不新增任何端點——api 以 `/ws` 握手成功（收到 `system/connected`）為準，web 以入口位址有回應為準，worker 沿用 007 已交付的 heartbeat 探針；「全部就緒」為複合訊號（seed 完成 → api 握手通 → web 入口有回應 → worker heartbeat 正常）。理由：api 對外僅有 `POST /diagnoses`、無任何 GET，探 HTTP port 實為「把 404 當健康」，只能證明行程在聽、證明不了 Gateway 已掛載；`/ws` 握手證明的正是 demo 所需的真實能力，且與 007 的探針形狀一致（映像內附探測腳本，`ws` 已是 api 正式相依）。**已知限制**：不涵蓋 Mongo／Redis 連通性——該深度屬 Feature 009 的觀測基線，008 明確不做（ADR-002 §5.3 已將 `/healthz` 劃歸 009；於 008 提前實作將推翻既定範圍並產生註定被重寫的半成品）。

## User Scenarios & Testing *(mandatory)*

本 feature 的「使用者」有三種：**展示者／評估者**（拿到 repo 想在最短時間內看到系統跑起來、走完 demo 劇本的人，含面試場景中的旁觀者）、**運維者**（期待 Gateway 這個最關鍵的行程崩潰後能自我復原的人）與**開發者**（日常在本機改 code、不希望開發體驗被改變的人）。

現況痛點：Feature 007 已把 worker 收進受監督的容器形態，但 **api（Gateway）與 web 仍只能在 host 上各開一個終端機用 dev 工具跑**。這造成兩個具體損失：

- **後果最重的行程反而沒人看管**：Gateway 一崩，所有 WebSocket 連線、訂閱表與 jobId 路由同時蒸發，而它沒有任何 restart 策略——007 只監督了錯誤後果較輕的那個行程（ADR-002 §5.1）。
- **啟動門檻與第一印象**：要看到畫面必須先備妥 Node 與套件管理器、裝依賴、複製兩份設定檔、開四個終端機。對只想「看它跑起來」的評估者，這道門檻與專案本身的技術含量無關，卻是他遇到的第一件事。

本 feature 的價值：把**執行形態**這個差距整棧收掉——三端都具備可部署的受監督形態，並讓展示者以**單一指令**起完整系統、以**單一入口位址**看到監控台走完 demo 劇本。這是生產化三部曲（007 → 008 → 009）的第二步，性質是**純打包**：背壓、佇列、streaming、快取、認證的語意一律不動（ADR-002 §5.2）——因此驗收的判準是「行為與現行模式逐項一致」，任何行為差異都算缺陷而非改良。

唯一的例外是 api 的**優雅關閉處理**：clarify 階段查證發現 api 現況根本沒有停止訊號處理（收到 SIGTERM 即刻死亡，既有的 `onModuleDestroy` 從未被觸發），而一個無法處理停止訊號的行程稱不上「可部署形態」——這屬於 ADR-002 §3 列為最大差距的「執行模型缺席」，並非打包以外之事。該例外的範圍嚴格限縮在關閉路徑（見 FR-004、FR-014）。

各 User Story 依優先級可獨立開發、獨立驗收，以 phase-by-phase 漸進交付。

### User Story 1 - Gateway 的受監督可部署形態（Priority: P1）

運維者以單一指令啟動 api（Gateway）的容器化受監督形態（連同既有 infra 與 007 的受監督 worker）。監控台連上後，遙測推送、訂閱過濾、心跳、診斷觸發與 AI 串流轉發的行為，與現行 host 直跑模式逐項一致。當 Gateway 因非預期錯誤以非零碼結束時，監督者自動以乾淨行程重啟，展示者不需人工介入即可重新連線繼續 demo；下達停止指令時，Gateway 在寬限期內收尾、不觸發重啟。

**Why this priority**: 這是本 feature 價值最高、風險最集中的一塊——Gateway 崩潰的後果比 worker 更重（連線、訂閱表、路由全滅），而它現在完全無人看管；ADR-002 §5.1 正是以此為由把 api 容器化從「如需另案」升格為排程。它也是 US2 一鍵 demo 的前置（沒有 api 容器就沒有全棧）。單獨交付即已把「後果最重的行程無監督」這個缺口補上，故列 P1。

**Independent Test**: 以單一指令起 infra + api（+ 007 worker），用現行本機前端連上這個容器化 Gateway，走一輪遙測、背壓比值、診斷 streaming 與快取命中，確認與 host 直跑模式一致；再強制終結 api 容器，確認它自動重啟且前端可重新連線；最後下停止指令，確認寬限期內收尾且不被重啟——即可獨立驗收。

**Acceptance Scenarios**:

1. **Given** infra 就緒且未啟動任何 host 端 api，**When** 運維者以單一指令啟動容器化 Gateway，**Then** 監控台可建立即時連線並持續收到遙測，畫面上的背壓比值與現行模式同量級。
2. **Given** 容器化 Gateway 正在服務中，**When** 展示者從監控台觸發一筆診斷，**Then** AI token 串流逐字出現、最終結果通過結構驗證、重複同簽章的診斷命中快取——與現行模式行為一致。
3. **Given** 容器化 Gateway 正在服務中，**When** 該行程以非零碼異常結束，**Then** 監督者自動以乾淨行程重啟，且前端重連後可恢復訂閱與遙測。
4. **Given** 容器化 Gateway 正在服務中，**When** 運維者下達停止指令，**Then** Gateway 在寬限期內完成收尾並以正常結束碼退出，監督者不再重啟它。
5. **Given** infra（資料層）尚未就緒，**When** 整組服務同時啟動，**Then** Gateway 不會因搶先連線而卡在失敗狀態——最終仍能自行進入可服務狀態。

### User Story 2 - 一鍵起全棧、單一入口走完 demo（Priority: P2）

展示者在一台只有容器執行環境與此 repo 的機器上，準備好必要祕密後下**一道指令**，即可起完整系統（前端、Gateway、worker、資料層）；接著只需打開**一個入口位址**，就能在監控台完整走完 demo 劇本——即時遙測、背壓比值、AI 診斷 streaming、快取命中。過程中不需要安裝 Node 或套件管理器、不需要裝依賴、不需要開多個終端機。

**Why this priority**: 這是本 feature 對外的主要回報（第一印象與可攜性），但它依賴 US1 的 api 容器；且即使沒有它，US1 已交付「Gateway 受監督」的核心價值。故列 P2。

**Independent Test**: 在乾淨環境（僅具容器執行環境 + clone repo + 填妥祕密）下單一指令啟動，開啟入口位址，逐項走完 demo 劇本並確認四個賣點都可見——即可獨立驗收。

**Acceptance Scenarios**:

1. **Given** 一台只裝了容器執行環境、剛 clone repo 並依範本填妥祕密的機器，**When** 展示者執行單一啟動指令，**Then** 前端、Gateway、worker 與資料層全部進入可服務／健康狀態，無需任何額外安裝步驟。
2. **Given** 全棧已啟動，**When** 展示者在瀏覽器開啟單一入口位址，**Then** 監控台載入並自行建立即時通道，持續顯示遙測——不需要使用者手動指定後端位址。
3. **Given** 全棧已啟動，**When** 展示者觸發診斷，**Then** 診斷工作由 worker 消化、token 經 Gateway 逐字轉發到畫面、結果落地並於重試時命中快取。
4. **Given** 示範所需的維修資料尚未存在，**When** 展示者執行單一啟動指令，**Then** 示範資料在 Gateway 開始服務前已自動備妥，展示者無需執行第二道指令；重複啟動 MUST NOT 造成資料重複堆積。
5. **Given** 全棧已啟動且示範資料已備妥，**When** Gateway 因故崩潰並自動重啟，**Then** 示範資料維持原狀、未被重置。

### User Story 3 - 開發模式零影響（Priority: P3）

開發者的日常迴圈完全不受本 feature 影響：既有的「只起 infra」啟動指令行為不變，app 仍在 host 上以熱重載方式執行，改 code 立即生效；容器化的全棧形態只在展示者明確要求時才啟動，不會在開發模式下被意外拉起。兩種模式的用途與指令在文件中清楚可辨。

**Why this priority**: 這是不可退讓的約束（ADR-002 §4.4：dev 迴圈不強制容器化，熱重載價值 > 監督價值），但它是「維持現狀」而非新增能力，且 US1／US2 的驗收本身就會觸碰到；故列 P3 獨立收尾。

**Independent Test**: 執行既有的「只起 infra」指令，確認只有資料層被啟動、沒有任何 app 容器被拉起；接著跑既有的 host 端開發流程，改一行前端與後端 code，確認熱重載照常生效——即可獨立驗收。

**Acceptance Scenarios**:

1. **Given** 開發者使用既有的「只起 infra」啟動指令，**When** 指令完成，**Then** 只有資料層服務在跑，前端／Gateway／worker 的容器皆未啟動。
2. **Given** 開發模式進行中，**When** 開發者修改前端或後端原始碼，**Then** 熱重載行為與本 feature 之前完全一致。
3. **Given** 展示者已用全棧模式跑過一輪並停止，**When** 開發者切回開發模式，**Then** 不需要額外清理步驟即可正常開發，兩種模式不互相干擾。

### User Story 4 - 乾淨收場與可重播（Priority: P4）

展示者在 demo 結束後以單一指令停止全棧，所有服務乾淨結束、不留孤兒行程；需要重來一次時，可將環境重設回初始狀態並重跑同一份劇本，得到可重現的結果。

**Why this priority**: 讓 demo 可反覆演練（憲章「可重播驗收」門檻），但它是在 US1／US2 之上的收尾能力，故列最後。

**Independent Test**: 全棧啟動後執行停止指令，確認所有服務結束；再執行連同資料一併清除的重設指令並重新啟動，確認系統回到初始狀態且劇本可重跑——即可獨立驗收。

**Acceptance Scenarios**:

1. **Given** 全棧正在運行，**When** 展示者執行停止指令，**Then** 所有服務在寬限期內結束，無殘留行程佔用連接埠。
2. **Given** 曾跑過一輪 demo（已產生遙測／診斷資料），**When** 展示者執行連同資料清除的重設並重新啟動，**Then** 系統回到初始狀態，同一份劇本可重跑並得到同等結果。

### Edge Cases

- **資料層尚未就緒即被連線**：api／worker 早於資料層進入可服務狀態時，不得永久卡死——需能自行恢復至可服務狀態（US1 場景 5）。
- **祕密缺漏**：LLM 金鑰未填時，全棧仍照常啟動、遙測與背壓比值正常運作（4 個賣點中的 2 個仍可見），僅 AI 診斷與快取命中失效並以既有錯誤路徑呈現——畫面訊息須指名「金鑰無效或未授權」為病因，而非通用失敗語。**MUST NOT 為此把缺金鑰升級為啟動失敗**：那會讓沒有 LLM 帳號的評估者一個賣點都看不到，違反 US2 的價值主張（決策理由見 Clarifications）。詳見 FR-017。
- **連接埠被佔用**：入口位址或資料層連接埠已被 host 上其他行程佔用時，啟動失敗需可診斷，且不得污染既有的開發模式流程。
- **同時啟動兩種模式**：開發模式（host 端 app）與全棧模式若同時啟動，資源衝突需可預期、可辨識，文件需說明不應混跑。
- **重複啟動／重複備妥示範資料**：重跑啟動指令不得造成示範資料重複堆積或狀態損壞（US2 場景 4）。
- **示範資料備妥失敗**：一次性 seed 服務若失敗（如資料層不可用），api 的啟動條件不成立——此時 MUST 以可辨識的訊息呈現失敗原因，MUST NOT 讓展示者面對一個「畫面在跑但診斷永遠沒有佐證資料」的半殘狀態。
- **祕密外洩防線**：任何映像產物都不得含有祕密——祕密只在執行時注入（憲章 VI）。
- **入口位址非預設值**：demo 環境改用其他入口連接埠或主機時，前端仍須能連上其後端通道（同源相對路徑使此情境自然成立，驗收時 MUST 實測一次非預設連接埠）。
- **首次啟動的建置成本**：第一次啟動需要建置映像時，等待時間需在文件中預告，避免被誤判為卡住。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 為 api（Gateway）提供可部署的容器化執行形態，其對外行為（遙測推送、訂閱過濾、心跳、診斷觸發、AI 串流轉發、認證語意）MUST 與現行 host 直跑模式逐項一致。
- **FR-002**: 系統 MUST 為 web（監控台前端）提供可部署的容器化執行形態，由建置產物提供靜態畫面服務，其視覺與互動 MUST 與現行開發模式一致。
- **FR-003**: 容器化的 api MUST 受監督：非零碼結束時自動以乾淨行程重啟，連續失敗達 **5 次**後停止重啟以防崩潰迴圈（沿用 007 worker 的監督語意）；正常結束（優雅關閉，結束碼 0）MUST NOT 觸發重啟。
- **FR-004**: api MUST 具備優雅關閉處理：收到停止訊號時 MUST 關閉既有連線與資源（Gateway、Mongo、Redis／佇列事件連線）後以結束碼 0 退出，停止寬限期為 **15 秒**。
  **註（前提修正）**：api 現況**不具**任何停止訊號處理——收到停止訊號即刻死亡，既有的資源釋放邏輯從未被執行（查證細節見 Clarifications）。故本項為**新增**行為而非沿用既有流程，並構成 FR-014 的窄範圍例外（見該項）。寬限期 15 秒依 api 自身收尾成本（僅關閉連線，量級為秒內）訂定，MUST NOT 照抄 worker 的 45 秒（該值為涵蓋 LLM 收尾預算而設，api 不呼叫 LLM）。
- **FR-005**: 系統 MUST 讓展示者以**單一指令**啟動完整系統（前端、Gateway、worker、資料層），且啟動前的前置需求 MUST 只有：容器執行環境、此 repo、依範本填妥的祕密。
- **FR-006**: 展示者 MUST 能只透過**單一入口位址**完成整個 demo 劇本——前端載入後 MUST 自行建立即時通道與觸發診斷，MUST NOT 要求使用者手動指定後端位址。全棧模式 MUST 只對外暴露這一個入口：即時通道與診斷觸發 MUST 以**同源相對路徑**進行、由入口反向代理轉發至 Gateway，Gateway MUST NOT 另行對外暴露連接埠。
- **FR-007**: 既有的「只起 infra」啟動指令行為 MUST 維持不變（只起資料層），app 的容器化形態 MUST NOT 在該模式下被自動拉起；host 端的熱重載開發流程 MUST 不受影響。
- **FR-008**: 兩種執行模式（開發模式、全棧 demo 模式）MUST 以同一份編排設定描述，MUST NOT 產生第二份平行的執行模型定義。模式切分 MUST 收斂為**單一** `demo` 分組並涵蓋 web／api／worker 三端；007 交付的 `supervised` 分組 MUST 退場（更名為 `demo`），MUST NOT 與新分組並存。全棧模式 MUST 以**單一分組旗標**啟動；三端 MUST NOT 在開發模式（不帶分組）下被自動拉起。單獨啟動某一端的需求 MUST 以指名服務滿足，MUST NOT 為此新增額外分組。
- **FR-009**: 服務之間的定址 MUST 以編排內的服務名解析，MUST NOT 依賴 host 迴路位址；瀏覽器端的定址 MUST 收斂為單一入口位址。前端產物 MUST NOT 內嵌後端絕對位址（同源相對路徑之故），使同一份產物在不同入口連接埠／主機下皆可用、無需重新建置。設定與祕密的注入方式 MUST 在三端間一致並文件化。
- **FR-010**: 系統 MUST NOT 把任何祕密烘入映像產物；祕密 MUST 僅於執行時注入（憲章 VI），且 MUST 僅提交設定範本。
- **FR-011**: 全棧模式 MUST 具備健康判定，讓展示者能辨識「全部就緒、可以開始 demo」的時點，而非只能靠肉眼猜測。判定 MUST 以**既有對外介面**為依據、MUST NOT 新增任何端點：api 以即時通道握手成功（收到連線確認）為準——MUST NOT 以「HTTP 連接埠有回應」充數（該探法只證明行程在聽，證明不了即時通道已可服務，理由見 Clarifications）；web 以入口位址有回應為準；worker 沿用 007 已交付的探針，MUST NOT 變更。「全部就緒」MUST 為複合訊號（示範資料備妥 → api 可握手 → web 入口有回應 → worker 探針正常）。
  **已知限制（明文接受）**：本判定 MUST NOT 涵蓋 Mongo／Redis 連通性——api 可能握手成功但資料層斷線而仍顯示健康。該深度屬 Feature 009 的觀測基線範圍，008 明確不做。
- **FR-012**: demo 劇本所需的示範資料（維修紀錄）MUST 於全棧啟動時由**一次性服務**自動備妥——每次啟動執行一次、完成即結束，api MUST 以其成功完成為啟動條件；展示者 MUST NOT 需要為此執行第二道指令或在 host 上安裝任何語言執行環境。該服務 MUST 復用既有的資料備妥邏輯（現行語意為重置後重建，結果決定性、重複執行不堆積），MUST NOT 為此改寫其語意。api 的崩潰自動重啟（FR-003）MUST NOT 觸發示範資料重置——資料備妥 MUST 只發生在全棧啟動時。
- **FR-013**: 系統 MUST 提供單一停止指令讓全棧乾淨收場，並 MUST 提供連同資料清除的重設方式，使 demo 可重播且重設後重起能回到初始狀態。
- **FR-014**: 本 feature MUST NOT 變更任何執行語意——背壓與批次提交、佇列與重試、雙通道 streaming、快取與去重、資料落地與認證的行為一律不動；任何可觀察的行為差異 MUST 視為缺陷。
  **唯一例外（窄範圍、明文授權）**：FR-004 為 api 新增的優雅關閉處理。該例外 MUST 僅限停止訊號的收尾路徑，MUST NOT 順帶調整上列任何執行語意；ADR-002 §6.4 已接受的有損寫入語意（in-flight 遙測可丟失）MUST 維持不變——本 feature MUST NOT 藉關閉路徑把它改為不可丟失。
  **不構成例外者**：FR-017 條件性的錯誤訊息映射補齊——該項為既有訊息映射的覆蓋缺口修復（同一類錯誤本應命中既有條目），MUST NOT 改變任何錯誤的觸發時機、重試次數或事件流，僅在既有映射漏接時補上對應字串。
- **FR-015**: `README.md` 與實作指南的啟動說明 MUST 更新為雙軌（開發模式 vs 一鍵 demo），清楚標示各自的用途、指令與前置需求；既有的開發模式入口 script MUST 保留。
- **FR-016**（跨 Feature 回補）: `supervised` → `demo` 的更名 MUST 同步落地至所有既有真實來源——`README.md` 的受監督模式指令、`apps/worker/Dockerfile` 的檔頭註解（該句敘述的是「現在怎麼建置這個映像」，屬現況描述）、實作指南 §14（現況）與 §16（啟動說明）——使全案 MUST NOT 殘留指向已退場分組名的敘述；回補 MUST NOT 重寫歷史（007 的決策背景保留原敘述，僅更新現況描述）。
  **註（analyze 修正）**：起草時列舉的「實作指南 §13（Feature 007 章節）」經全域搜尋確認**不含任何分組名字面**——§13 通篇為 007 的決策背景與待決問題（「compose profile？獨立 script？」），分組名是 007 實作期才定的，從未寫回 §13。故 §13 依「不重寫歷史」原則**不動**，不再列為更名標的；指南的實際回補處為 §14（現況已落地）與 §16（啟動說明雙軌化，見 FR-015）。
- **FR-017**: LLM 金鑰未填時，全棧 MUST 照常啟動且 MUST NOT 因此擋下任何服務——遙測與背壓比值 MUST 正常運作；AI 診斷 MUST 沿用既有錯誤路徑失敗，MUST NOT 新增啟動前祕密檢查（無論置於編排、app 啟動路徑或獨立服務）。畫面呈現的失敗訊息 MUST 指名金鑰為病因、MUST NOT 只顯示通用失敗語。驗收 MUST 實測「金鑰留空」的完整路徑（空金鑰與無效金鑰的供應商回應可能不同，故 MUST NOT 以無效金鑰的結果推斷）；若既有訊息映射未命中而落入通用文案，MUST 補齊該映射——此屬覆蓋缺口的缺陷修復（見 FR-014「不構成例外者」），MUST NOT 藉此擴張為新的檢查機制。訊息文案 SHOULD 對自助使用者可行動（指名應填的設定項與其所在範本），MUST NOT 假設使用者另有管理員可聯繫。`README.md` 與設定範本 MUST 載明此症狀與其成因。

### Key Entities

- **執行模式（Execution Mode）**：系統可被啟動的形態。有兩種——**開發模式**（只起資料層，app 在 host 熱重載）與**全棧 demo 模式**（三端與資料層全部以受監督容器執行）。兩者由同一份編排設定描述，以分組方式切換。
- **服務（Service）**：編排中的一個可執行單元（web、api、worker、seed、redis、mongo）。屬性含：所屬模式分組、依賴關係、重啟策略、健康判定、停止寬限期、設定與祕密來源。其中 **seed 為一次性服務**——執行一次即結束、不受監督重啟，是 api 的啟動前置。
- **映像產物（Image）**：由 repo 源碼建置出的可部署封裝，MUST 不含祕密。
- **入口位址（Entry Point）**：展示者在瀏覽器開啟的單一位址，是 demo 期間唯一需要知道的位址。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在一台只具備容器執行環境的乾淨機器上，從「clone 完成且祕密已填妥」到「監控台可見即時遙測」，展示者只需執行 **1 道指令**、開啟 **1 個位址**，且**不需安裝任何語言執行環境或套件管理器**。
- **SC-002**: 全棧啟動後，`docs/Flow-Gatekeeper-SDD-完整實作指南.md` 的 demo 劇本 **4 個賣點（即時遙測、背壓比值、AI 診斷 streaming、快取命中）100% 可在單一入口位址下重現**，且每一項的可觀察行為與現行模式一致。
- **SC-003**: Gateway 行程被強制終結後，**不需任何人工介入**即自動恢復服務，且前端可在 **30 秒內**重新連上並繼續收到遙測。
- **SC-004**: 開發模式**零回歸**：既有「只起 infra」指令啟動的服務清單與本 feature 之前**完全相同**（無新增被自動拉起的服務），host 端熱重載開發流程的步驟數不變。
- **SC-005**: 停止指令執行後，**100% 的服務在各自寬限期內自行結束**（api 的收尾實測 MUST **≤ 3 秒**、無需被強制終結），**0 個殘留行程佔用相關連接埠**；資料清除後重新啟動，同一份 demo 劇本可**重跑並得到同等結果**。
  **註（3 秒門檻的由來）**：api 的收尾僅為關閉 ws 連線、Mongo client 與 Redis 訂閱連線，量級為秒內；3 秒已給足餘裕，且距 15 秒寬限期上限有 5 倍距離，使「遠低於上限」成為可客觀判定的判準而非驗收者的主觀認定。**超過 3 秒即屬缺陷**——代表收尾路徑有非預期阻塞，正解是排除該阻塞，MUST NOT 藉調大寬限期或本門檻來讓驗收通過。
- **SC-006**: 交付的映像產物中**祕密數量為 0**（可由產物內容檢視佐證），設定範本以外的祕密檔案**未進入版控**。
- **SC-007**: 新讀者只讀 `README.md` 即能在**不詢問任何人**的前提下，正確選出自己要用的模式並完成啟動；兩種模式的指令、用途與前置需求在文件中各自成段、不混淆。

## Assumptions

- **前置條件已滿足**：Feature 007 已併回 `develop`，worker 的容器化形態、受監督語意（非零退出即重啟、重啟上限、寬限期）與健康探針皆已落地；本 feature 沿用其既定模式，不重議監督者選型（ADR-002 §2、§4 為既定約束）。
- **監督者即編排器的重啟策略**：ADR-002 §2 已定案容器化路線；本 spec 中的「監督者」一律指此既定選型，不再評估替代方案。
- **demo 走明文本機**：入口位址為本機明文位址，不涉及 HTTPS、TLS 終結、憑證或網域（ADR-002 §7、指南 §14.2「明確不做」）。反向代理僅用於「單一入口 + 同源路徑」這個用途，MUST NOT 擴充為生產級的邊緣配置（TLS、快取、限流、多站台路由皆不在範圍）。
- **不含發布管線**：映像發布至 registry、雲端部署、編排平台、CI/CD 一律不在範圍內（ADR-002 §7、§9 CI 目前刻意暫停）。
- **不補既有的四項運維差距**：Gateway 水平擴展、Pub/Sub at-most-once、認證升級、有損寫入語意維持 ADR-002 §6 的「只文件化」處置，本 feature 不動。
- **可觀測性留給 009**：結構化日誌、healthz 端點與關鍵指標屬 Feature 009 的範圍；本 feature 只做「全棧就緒與否」層級的健康判定，不建立觀測基線。
- **祕密仍以各 app 自帶設定範本為準**：現行「每個 app 一份設定」的形狀為既有事實；本 feature 只收斂其在容器情境下的注入與定址方式，不重新設計設定佈局。
- **實作機制留待 `/speckit-plan` 定案**：入口拓樸已由 Clarifications 定為「前端容器內建反向代理、單一入口、同源相對路徑」（連帶使指南 §14.3 的「後端位址注入時機」一問失去適用前提——同源即無位址可注入）；但**用何種伺服器軟體**提供靜態檔與反向代理仍屬實作取捨，本 spec 只規範可觀察的結果，不預設機制。
- **單機單實例**：demo 僅需單一 Gateway 實例；多實例與負載平衡不在範圍（ADR-002 §6.1）。
