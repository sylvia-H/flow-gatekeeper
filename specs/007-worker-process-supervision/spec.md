**Status**: Draft

## Clarifications

### Session 2026-07-08

- Q: 故障注入旗標應支援哪些注入時點? → A: 兩種語意時點——「啟動後立即」（供 US4 崩潰迴圈演練）與「處理工作中」（供 US2 進行中工作重派驗收），皆可確定性重現、不靠時間競賽。
- Q: 監督者的重試上限（連續失敗幾次後停止重啟）設多少? → A: 5 次——足以觀察退避間隔逐次遞增，演練時間可控。
- Q: 存活訊號與健康判定參數怎麼設? → A: 心跳每 10 秒發送、有效期 30 秒；健康檢查每 30 秒、連續 3 次失敗判不健康（約 90 秒內反映），滿足 SC-005 的 2 分鐘上限且留餘裕、容忍繁忙高峰。
- Q: 開發模式與受監督模式的切換機制用哪種? → A: 以同一份 compose 設定的 profile 分組——既有啟動指令照舊只起 infra（開發模式零影響），受監督模式以附加 profile 的單一指令啟動；單一檔案、單一真實來源。
- Q: 致命錯誤後的退出策略用哪種? → A: 立即結束——記錄致命訊息後直接以非零碼退出，不嘗試關閉連線，重建交給重啟後的乾淨行程；與優雅關閉路徑界線最清楚。

## User Scenarios & Testing *(mandatory)*

本 feature 的「使用者」有兩種：**運維／展示者**（把系統以貼近生產的形態跑起來、遇到故障時期待系統自我復原的人）與**開發者**（日常在本機開發、不希望開發體驗被改變的人）。

現況痛點：worker 遇到非預期致命錯誤時採「記錄後原地續跑」——因為專案目前**沒有任何行程監督者**，若直接改成「錯誤即結束」，worker 死了就沒人重啟、佇列中的診斷工作全部無人消化，比現況更糟。但「原地續跑」本身是暫時解：致命錯誤後行程狀態未定義，續跑會悄悄產出錯誤結果並遮蔽真正的 bug。**「錯誤即結束（let it crash）」與「監督者自動重啟」是同一件事的兩半，必須一起交付**。

本 feature 的價值：給 worker 一個**受監督的可部署執行形態**（監督者選型已由 ADR-002 定案為容器化路線，本 spec 視為既定約束、不再重議），把崩潰語意翻轉為「記錄致命 → 結束 → 由監督者以乾淨行程重啟」，並補上「活著但卡住」的健康判別與可重現的故障演練機制。這是生產化三部曲（007 → 008 → 009）的第一步，也是唯一一個**行為翻轉**（其後 008 為純打包、009 為觀測基線）。

各 User Story 依優先級可獨立開發、獨立驗收，以 phase-by-phase 漸進交付。

### User Story 1 - 受監督的可部署執行形態（Priority: P1）

運維／展示者以單一指令啟動 worker 的受監督執行形態（連同既有本機 infra），worker 能端到端消化診斷工作——快取、串流輸出、錯誤語意都與現行本機直跑模式一致；下達停止指令時，worker 走既有優雅關閉流程、在寬限期內收尾。開發者的日常本機開發流程完全不受影響。

**Why this priority**: 這是整個 feature 的載體——沒有可部署的受監督形態，「錯誤即結束」的翻轉（US2）就不能合併（只做一半是退步）。它本身不改任何行為語意，風險可控、可先行驗收，故列 P1 之首。

**Independent Test**: 以單一指令啟動受監督 worker，從監控台觸發一筆診斷，確認串流 token、診斷結果、快取命中與錯誤語意與本機直跑模式一致；再下停止指令，確認在寬限期內優雅收尾——即可獨立驗收。

**Acceptance Scenarios**:

1. **Given** 本機 infra 已就緒，**When** 運維者以單一指令啟動受監督形態的 worker，**Then** worker 成功建置並啟動，開始消化診斷工作，串流輸出與診斷結果與本機直跑模式一致。
2. **Given** 受監督 worker 執行中，**When** 對同一機台、同一嚴重度重複觸發診斷，**Then** 快取行為與本機直跑模式一致（命中快取、不重複消耗 LLM 額度）。
3. **Given** 受監督 worker 執行中且有工作在處理，**When** 運維者下達停止指令，**Then** worker 走既有優雅關閉流程，在停止寬限期內完成收尾（關閉工作消化、釋放外部連線），不被強制中斷、不遺留半開連線。
4. **Given** 開發者使用既有本機開發流程（熱重載直跑），**When** 本 feature 交付後照常開發，**Then** 開發流程與啟動腳本照常可用，文件清楚說明「開發模式」與「受監督模式」各自的使用情境與切換方式。

### User Story 2 - 致命錯誤後系統自我復原（let it crash）（Priority: P1）

運維／展示者面對 worker 發生非預期致命錯誤（未捕捉例外、未處理拒絕）時，系統的行為是：worker 記錄明確的致命訊息後**結束行程**（不再原地續跑），監督者偵測到行程結束後**自動以乾淨行程重啟**；重啟後，崩潰當下進行中與佇列中的診斷工作**最終都被重新消化**（或走既有的錯誤／重試語意），不會永久卡死。整段「致命 → 結束 → 重啟 → 恢復消化」可從記錄中判讀，全程無需人工介入。

**Why this priority**: 這是本 feature 存在的理由——把「悄悄產出錯誤結果」的暫時策略翻轉為生產正解。它是三部曲中唯一的行為翻轉，需驗證工作重派與優雅關閉的交互，風險最高、價值最大，故列 P1。依賴 US1 的監督者就位（先後關係），但可用獨立場景驗收。

**Independent Test**: 在受監督形態下（可用 US3 的故障注入旗標）觸發一次致命錯誤，觀察 worker 記錄致命訊息並結束、監督者自動重啟、崩潰當下的進行中工作被重新消化——即可獨立驗收。

**Acceptance Scenarios**:

1. **Given** 受監督 worker 執行中，**When** 發生未捕捉例外或未處理拒絕，**Then** worker 記錄明確標示「致命、將交由監督者重啟」的訊息後結束行程，不原地續跑。
2. **Given** worker 因致命錯誤結束行程，**When** 監督者偵測到行程結束，**Then** 自動啟動一個乾淨的新行程，且記錄可判讀「致命 → 重啟」的先後順序。
3. **Given** 崩潰當下有進行中的診斷工作與佇列中待處理的工作，**When** worker 重啟完成，**Then** 這些工作最終被重新消化或走既有錯誤／重試語意，不會永久卡死；錯誤與重試語意與本 feature 之前的行為一致。
4. **Given** worker 正在優雅關閉流程中（收到停止指令），**When** 關閉過程中發生錯誤或致命事件，**Then** 致命退出路徑與優雅關閉路徑不互相干擾——行程仍在寬限期內終止，不卡住、不遺留半開連線。
5. **Given** 開發模式（熱重載直跑、非受監督），**When** 發生致命錯誤，**Then** 行為與文件說明一致（行程結束後等待人工或檔案變更觸發重啟，屬已知且已文件化的差異）。

### User Story 3 - 可重現的故障演練機制（Priority: P2）

運維／展示者能以環境設定開啟一個**故障注入旗標**，讓 worker 以可控方式拋出指定型態的致命錯誤（未捕捉例外或未處理拒絕），且可指定注入時點——「啟動後立即」（演練崩潰迴圈）或「處理工作中」（演練進行中工作重派）——用來重現與演練 US2 的自我復原路徑——不需修改程式碼、不需重新建置。旗標為正式交付：預設關閉、有文件說明僅供演練；未來的「故障演練 demo」（監控台監控它自己的死而復生）將重複使用同一機制。

**Why this priority**: 它是 US2 驗收的注入手段，也是日後 demo 敘事的正式機制；沒有它，崩潰驗收只能靠臨時改 code 拋錯，不可重現。列 P2 是因為它服務於 US2 的可重現性，本身不改變系統正常行為。

**Independent Test**: 未設定旗標時確認 worker 行為完全正常；以環境設定開啟旗標並指定錯誤型態，啟動 worker，確認在可控時點拋出對應致命錯誤；關閉旗標後行為恢復正常——全程不改 code、不重建——即可獨立驗收。

**Acceptance Scenarios**:

1. **Given** 故障注入旗標未設定，**When** worker 以任一模式啟動與運行，**Then** 行為與沒有此機制時完全相同（預設關閉、零影響）。
2. **Given** 以環境設定開啟旗標並指定「未捕捉例外」型態，**When** worker 啟動，**Then** worker 在指定的注入時點（「啟動後立即」或「處理工作中」）拋出對應致命錯誤，觸發 US2 的「致命 → 結束 → 重啟」路徑。
3. **Given** 以環境設定開啟旗標並指定「未處理拒絕」型態，**When** worker 啟動，**Then** 同上，且兩種型態皆可分別重現。
4. **Given** 以環境設定指定注入時點為「處理工作中」，**When** worker 取得一筆診斷工作開始處理，**Then** 在該工作處理期間拋出致命錯誤——供 US2 場景 3（進行中工作重派）確定性重現。
5. **Given** 演練結束，**When** 移除旗標設定並重啟，**Then** worker 恢復完全正常行為；上述演練全程不需修改程式碼或重新建置。

### User Story 4 - 崩潰迴圈防護可觀察（Priority: P2）

運維／展示者面對 worker 反覆快速失敗（例如設定錯誤導致啟動即崩潰）時，監督者的重啟間隔**逐次遞增**（退避），且在達到重試上限後**停止重啟**——避免熱迴圈打爆 LLM 額度與資料庫連線；「已達上限、停止重啟」的狀態可從記錄與狀態查詢中判讀。

**Why this priority**: 沒有崩潰迴圈防護，「自動重啟」在故障持續存在時反而變成自動放大器。防護能力由監督者內建承接（不自行造輪子），本 feature 的工作是**驗證**其行為並確保可判讀，故列 P2。

**Independent Test**: 以故障注入旗標使 worker 啟動即崩潰，觀察多次重啟的間隔逐次遞增；達上限後確認不再重啟、且能從狀態查詢與記錄判讀「已停止」——即可獨立驗收。

**Acceptance Scenarios**:

1. **Given** worker 因持續存在的故障連續快速失敗，**When** 監督者反覆重啟，**Then** 重啟間隔逐次遞增（退避），可從記錄或狀態查詢觀察到。
2. **Given** 連續失敗達到重試上限，**When** 監督者停止重啟，**Then** worker 維持停止狀態、不再進入熱迴圈，且「已達上限停止」可從狀態查詢與記錄判讀。
3. **Given** 崩潰迴圈期間，**When** 每次重啟的行程短暫存活，**Then** 對外部資源（LLM 額度、佇列、資料庫）的消耗受退避節制，不出現無間隔的熱迴圈連打。

### User Story 5 - 「活著但卡住」可被察覺（Priority: P3）

運維／展示者能判別 worker「行程還活著、但已經不做事」（活鎖／卡死）的情境：worker 週期性發出存活訊號，監督層據以判定健康狀態；當存活訊號停止超過判定門檻，健康狀態轉為「不健康」且可從狀態查詢觀察——補上「行程死亡偵測」涵蓋不到的盲點。

**Why this priority**: 行程死亡由監督者的重啟機制涵蓋（US2／US4），但「活著卻卡住」偵測不到——這是監督完整性的最後一塊。健康判定屬「可觀察的示警」定位（不自動重啟），影響面小，故列 P3。

**Independent Test**: worker 正常運行時確認健康狀態為「健康」；人工使存活訊號停止（模擬活鎖），超過判定門檻後確認健康狀態轉為「不健康」且可觀察——即可獨立驗收。

**Acceptance Scenarios**:

1. **Given** 受監督 worker 正常運行，**When** 查詢其健康狀態，**Then** 顯示為健康（存活訊號在有效期內持續更新）。
2. **Given** worker 行程存活但停止發出存活訊號（人工模擬活鎖），**When** 超過健康判定門檻，**Then** 健康狀態轉為不健康，且可從狀態查詢觀察到。
3. **Given** 健康狀態為不健康，**When** 運維者查看記錄與狀態，**Then** 能區分「行程死亡（已由監督者處理）」與「活著但卡住（需人工介入）」兩種情境。

### Edge Cases

- **停止指令與致命事件重疊**：優雅關閉進行中發生致命錯誤時，兩條路徑不得互相干擾——行程仍須在寬限期內終止，不卡住、不遺留半開連線（US2 場景 4）。
- **寬限期不足**：停止寬限期必須涵蓋「收尾進行中工作、釋放外部連線」所需時間；若收尾超時被強制中斷，進行中工作依既有重派語意由下次啟動消化。
- **重複消化的邊界**：崩潰當下進行中的工作在重啟後可能被重新執行（至少一次語意）；本 feature 沿用既有的工作級錯誤／重試／快取語意，不新增去重機制，也不調整工作級重試策略。
- **開發模式的致命錯誤**：熱重載直跑模式下沒有監督者，行程結束後停在「等待檔案變更」而非自動重啟——此為已知差異，必須在文件中寫明。
- **存活訊號的誤判**：健康判定門檻須容忍正常的繁忙高峰（處理中短暫延遲發訊號），避免把「忙」誤判為「卡死」。
- **不健康之後**：健康判定為「可觀察的示警」，不自動觸發重啟；自動處置與系統性告警屬後續範圍（009 之後）。
- **崩潰瞬間的外部連線**：致命退出走「立即結束、交由重啟後重建連線」路徑時，不得遺留使外部服務（佇列、資料庫）不可用的殘留狀態。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供 worker 的受監督可部署執行形態，運維者能以單一指令（連同既有本機 infra）建置並啟動。
- **FR-002**: 受監督形態下的 worker MUST 端到端消化診斷工作，且快取、串流輸出、錯誤語意與現行本機直跑模式一致。
- **FR-003**: worker 遇到非預期致命錯誤（未捕捉例外、未處理拒絕）時 MUST 記錄明確標示「致命」的訊息後**立即以非零碼結束行程**（不嘗試關閉外部連線，重建交由重啟後的乾淨行程），MUST NOT 原地續跑；兩種錯誤來源與非 Error 值 MUST 以一致方式處理。bootstrap（啟動初始化）失敗同屬致命語意——同樣記錄後以非零碼結束，交由監督者依重啟策略處理。
- **FR-004**: 監督者 MUST 在 worker 行程結束（非正常停止）後自動以乾淨行程重啟；「致命 → 重啟」的先後順序 MUST 可從記錄判讀。
- **FR-005**: worker 崩潰重啟後，崩潰當下進行中與佇列中的診斷工作 MUST 最終被重新消化或走既有錯誤／重試語意，MUST NOT 永久卡死。
- **FR-006**: 連續快速失敗時，重啟間隔 MUST 逐次遞增（退避）；達重試上限（**5 次**）後 MUST 停止重啟，且「已達上限停止」MUST 可從狀態查詢與記錄判讀。
- **FR-007**: worker MUST 週期性發出帶有效期的存活訊號（發送週期 **10 秒**、有效期 **30 秒**）；監督層 MUST 據以判定健康狀態（檢查間隔 **30 秒**、連續 **3 次**失敗判為不健康），存活訊號停止超過門檻時 MUST 呈現為不健康且可觀察。健康判定定位為示警，不自動重啟。
- **FR-008**: 系統 MUST 提供以環境設定控制的故障注入旗標，可分別注入「未捕捉例外」與「未處理拒絕」兩種致命錯誤型態，並 MUST 支援「啟動後立即」與「處理工作中」兩種注入時點（前者供崩潰迴圈演練、後者供進行中工作重派演練）；旗標 MUST 預設關閉、關閉時零影響，且演練 MUST NOT 需要修改程式碼或重新建置。
- **FR-009**: 既有優雅關閉流程（停止訊號 → 收尾工作消化 → 釋放外部連線）MUST 照常運作，並在停止寬限期內完成；致命退出路徑與優雅關閉路徑 MUST 界線清楚、不互相干擾。
- **FR-010**: 開發者的既有本機開發流程（熱重載直跑與啟動腳本）MUST 不受影響；文件 MUST 說明「開發模式」與「受監督模式」的使用情境、切換方式，以及開發模式下致命錯誤不自動重啟的已知差異。
- **FR-011**: 文件與程式註解 MUST 與新崩潰語意一致——移除「暫時策略（記錄後續跑）」的但書描述。

### 範圍邊界（Out of Scope）

- api／web 的容器化與一鍵全棧 demo——排程在 Feature 008。
- 結構化日誌、api 健康端點、指標——排程在 Feature 009；本 feature 只做監督所需的最小存活訊號。
- 系統性告警與 unhealthy 自動處置——009 之後另議。
- 完整 CI/CD 發布管線、映像發布、雲端編排——ADR-002 明確拒絕／另議。
- 工作級重試策略（次數／退避）的調整——與行程級監督正交，不動。
- 監督者選型重議——已由 ADR-002 定案為容器化路線，pm2／systemd 出局。

### Key Entities

- **受監督執行形態**: worker 的可部署服務定義——含建置方式、對 infra 的依賴關係、重啟策略（退避與上限）、停止寬限期與健康檢查設定。
- **存活訊號（heartbeat）**: worker 週期性發出、帶有效期的「我還活著且在做事」訊號；是健康判定的依據。
- **故障注入旗標**: 環境層級的演練開關，指定要注入的致命錯誤型態（未捕捉例外／未處理拒絕）與注入時點（啟動後立即／處理工作中）；預設關閉，屬正式交付並文件化。
- **致命事件記錄**: 標示錯誤型態（未捕捉例外／未處理拒絕）、致命語意與「交由監督者重啟」意圖的記錄項，用於判讀「致命 → 重啟 → 恢復」的完整過程。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 運維者以單一指令即可啟動受監督 worker，啟動後以既有驗收場景重演診斷流程，結果（串流、快取、錯誤語意）與本機直跑模式一致，無需任何額外手動步驟。
- **SC-002**: 注入致命錯誤後，系統在 **60 秒內**自動恢復消化診斷工作（致命 → 結束 → 重啟 → 恢復），全程無人工介入。
- **SC-003**: 崩潰當下進行中與佇列中的診斷工作 **100%** 最終被消化或走既有錯誤語意，無任何工作永久卡死。
- **SC-004**: 崩潰迴圈情境（連續快速失敗）中，重啟間隔可觀察逐次遞增；達重試上限後 **10 分鐘內無新重啟**，且狀態可判讀為「已停止」。
- **SC-005**: 「活著但卡住」情境（存活訊號停止）在 **2 分鐘內**反映為不健康狀態並可觀察。
- **SC-006**: 故障演練不需修改程式碼或重新建置，同一演練**連續重演 3 次**結果一致（皆走完「致命 → 重啟 → 恢復」）。
- **SC-007**: 下達停止指令後，worker 在停止寬限期內完成優雅收尾（**0 個**遺留半開連線、**0 次**被強制中斷）。
- **SC-008**: 開發者照既有流程啟動本機開發環境，體驗與本 feature 交付前**無差異**（啟動腳本照常可用、熱重載照常運作）。

## Assumptions

- **監督者選型為既定約束**：ADR-002 已定案容器化路線（監督能力由容器編排的重啟策略承接），本 spec 不重議 pm2／systemd；「重啟退避」與「重試上限」使用監督者內建能力，本 feature 的工作是驗證與調校，不自行實作重啟邏輯。
- **雙模式並存**：開發模式保留現行熱重載直跑（熱重載價值 > 監督價值、人在場看記錄即可）；受監督模式用於 demo／貼近生產情境。切換機制已定案為同一份 compose 設定的 profile 分組（見 Clarifications）：既有 infra 啟動指令不變，受監督模式以附加 profile 啟動。
- **重啟策略預設帶重試上限**：預設「失敗才重啟、帶重試上限」以確保崩潰迴圈會停下且可判讀；上限已定案為 **5 次**（見 Clarifications），使用監督者內建能力設定。
- **健康判定門檻已定案**：心跳每 10 秒發送、有效期 30 秒；健康檢查每 30 秒、連續 3 次失敗判不健康（典型約 90 秒內反映；最壞情況——TTL 殘餘與檢查相位對齊——約 120 秒，見 Clarifications）；SC-005 的 2 分鐘為驗收上限（量測自存活訊號停止時點）、非實作參數。
- **工作重派沿用既有機制**：佇列系統既有的失敗偵測與重試機制足以讓崩潰當下進行中的工作被重派（本 feature 驗證之、不調整工作級語意）；重複執行以既有快取與錯誤語意承接（至少一次語意為已知取捨）。
- **致命退出採「立即結束」（已定案）**：致命錯誤後行程狀態未定義，不在退出前嘗試收尾——記錄致命訊息後立即以非零碼退出，連線重建交由重啟後的乾淨行程（見 Clarifications）；優雅關閉（停止指令觸發）與致命退出（錯誤觸發）為兩條互不重疊的路徑。
- **前置條件**：Feature 006 已併回 `develop`；本 feature 從 `develop` 開出 `007-worker-process-supervision` branch。
- **祕密與設定衛生沿用憲章**：受監督形態的環境設定注入不提交任何祕密，僅以範例檔記錄形狀。
