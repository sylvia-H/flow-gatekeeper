- Q: 側欄的機台清單在拓樸主畫面下是否保留？ → A: 移除側欄機台清單；側欄只留 Fleet Health、最近異常摘要列（可點選台）與主題切換；狀態燈與最近異常時間改由拓樸卡片與異常摘要列承載。
- Q: 桌機（≥1280 寬）未選取機台時，Copilot 面板要不要常駐展開？ → A: 所有寬度一律預設收合、選取機台後自動展開；可手動收合，收合／展開偏好記在本機。
- Q: 是否把鍵盤操作納入 013 範圍？ → A: 納入最小完整快捷鍵集（`/` 聚焦搜尋、搜尋剩一筆時 Enter 選取、方向鍵在卡片間移動、Enter 選台、`d` 診斷選取機台、Escape 關閉面板或取消選取）加「?」快捷鍵說明層；側欄與事件列的寬高拖曳把手支援鍵盤。
- Q: 異常標記（latch）的「操作者確認清除」要怎麼做？ → A: 卡片上的異常標記本身可點擊清除；側欄異常摘要列每列有清除動作；兩處操作同一份狀態、互相同步。

## User Scenarios & Testing *(mandatory)*

本 feature 的「使用者」有兩種，與 `apps/web/PRODUCT.md` 一致：**監控台操作者**（長時間盯著一組機台、異常時按一下拿到 AI 診斷的工程／維運人員）與**展示者／評估者**（拿到 repo 一鍵跑起來、要在 22 秒 demo 內看懂「背壓、串流、快取」三個機制的人）。

現況痛點（critique 20/40 的結論）：1.1.0 的介面工程紀律很好——高頻更新下版面不抖、狀態誠實、token 乾淨——但**把自己的賣點藏起來了**。背壓比值在 1440 桌機（drawer 展開）、1024 平板與手機全部不可見；逐字串流看起來像 worker log；Cached 只是一顆 11px 徽章；critical 幾秒就回 healthy 且不留痕跡；主畫面是任何監控產品都能套用的無序卡片網格，「致敬 Argo CD」只剩狀態點。視覺上它「乾淨但無個性」，連貫性來自克制而不是主張。

本 feature 的價值：**換一個視覺世界、把四個產品機制放到該被看見的位置、把主畫面升級成產線拓樸**，同時保留既有的工程紀律（高頻 buffer 批次提交、具名 token、無障礙規則、狀態誠實）與產品約束（首屏為監控台、卡片圓角上限、不用紫色漸層與光球、不用 Argo CD 品牌資產）。性質刻意壓在**純前端**：通訊契約（12 則 WS 訊息與一個 REST 端點）與後端行為一律不變，所有新呈現都只消費既有資料。

各 User Story 依優先級可獨立開發、獨立驗收，以 phase-by-phase 漸進交付。US1 是其他 story 的視覺地基，但每個 story 的**行為**驗收不依賴 US1 完成。

### User Story 1 - 新視覺世界與深淺雙主題（Priority: P1）

操作者與評估者打開監控台，看到的是一套**為這個產品而作**、而非品類通用的視覺世界：淺色為預設主題，可一鍵切換到深色主題，切換後所有面板、狀態色、圖表與文字同步換裝，不閃爍、不跳版；下次開啟記得上次的選擇。所有狀態（healthy／warning／critical／stale／reconnecting／failed）在兩個主題下都一眼可辨、不只靠顏色，且小字對比符合無障礙門檻。舊的深色單一主題與其規格文件退役，新的視覺系統成為前端唯一視覺真實來源。

**Why this priority**: 這是整個改版的地基——token、字體、面層、元件外觀全部由它決定，其他 story 的新元件都建在它之上。單獨交付即可讓評估者感受到「這不是另一個 Grafana」，直接兌現改版的主要訴求。故列 P1。

**Independent Test**: 在既有資訊架構上套用新視覺世界並提供主題切換；於四個驗收 viewport 分別在 light 與 dark 下截圖，確認狀態可辨、小字對比達標、切換無閃爍且重新載入後偏好保留——不需要拓樸或背壓 strip 就位即可驗收。

**Acceptance Scenarios**:

1. **Given** 使用者第一次開啟監控台，**When** 頁面載入完成，**Then** 介面以淺色主題呈現，且第一屏就是可操作的監控台（非 landing page）。
2. **Given** 使用者切換到深色主題，**When** 切換完成，**Then** 所有面板、狀態色、圖表、文字在同一幀內換裝，無白屏或閃爍，版面不位移；重新整理頁面後仍為深色。
3. **Given** 任一主題下有 healthy、warning、critical、stale 四種機台狀態同時存在，**When** 觀察卡片、側欄與聚合面板，**Then** 每種狀態都有顏色、文字標籤與輔助技術可讀的名稱三重編碼，且同一狀態在所有面板使用同一組語意色（stale 不再在卡片與聚合面板用不同顏色）。
4. **Given** 任一主題，**When** 量測所有功能性文字（含 10–12px 的徽章、單位、計數）對其底色的對比，**Then** 一般文字 ≥ 4.5:1，且不存在小於 11px 的功能性文字。
5. **Given** 改版完成，**When** 檢視專案的視覺真實來源，**Then** `apps/web/PRODUCT.md` 與 `apps/web/DESIGN.md` 是唯一指定來源，舊的 `design-spec.md` 標示為歷史文件、`refs/*.png` 已移除，憲章、CLAUDE.md、README、指南均指向新來源。

### User Story 2 - 背壓比值常駐可見（Priority: P1）

評估者在任何裝置、任何面板展開狀態下打開監控台，都能在首屏看到「每秒收到的遙測訊息數 → 每秒實際渲染的批次數」與兩者的比值，並從一條短時間窗的走勢線看出比值如何隨頻率累積。它是監控台的「心跳」，位置與重量都讓人第一眼就注意到，而不是工具列裡一顆隨寬度消失的徽章。

**Why this priority**: PRODUCT.md 明載背壓比值是核心賣點與「可見、可驗收」原則的直接體現；critique 列為唯一 P0。它與 US1 互不依賴，單獨交付即可讓 demo 的第一個賣點重新存在。故列 P1。

**Independent Test**: 在 1440×900（drawer 展開）、1366×768、768×1024、390×844 四個 viewport 下分別載入監控台，確認比值在不捲動、不收合任何面板的情況下可見；拉高 mock 頻率觀察比值與走勢線隨之變化。

**Acceptance Scenarios**:

1. **Given** 四個驗收 viewport 中的任一個、Copilot 面板展開，**When** 頁面載入完成且遙測開始抵達，**Then** 首屏不捲動即可見「訊息數／批次數／比值」三個數字，且比值以不小於機台卡片遙測值的字級呈現。
2. **Given** 遙測持續抵達，**When** 觀察 60 秒，**Then** 走勢線同時呈現訊息速率與渲染速率兩條曲線，比值數字與兩線的關係一致（訊息遠多於批次時比值明顯大於 1）。
3. **Given** 視窗縮到手機寬度，**When** 檢視首屏，**Then** 至少比值數字仍常駐可見，不因任何斷點被整體隱藏。
4. **Given** 有訊息因背壓被丟棄，**When** 丟棄數大於 0，**Then** 丟棄數以警示語意色顯示在同一區域，為 0 時不佔版面。

### User Story 3 - 產線 stage 拓樸主畫面（Priority: P2）

操作者打開主畫面，看到的不再是無序卡片網格，而是依產線順序排列的三個 stage 欄：Prep → Forming & Baking → Fulfilment，機台卡片歸屬各自的欄位，欄與欄之間有流向連線表達「物料往下游走」。critical 的機台在整條產線中的位置一目了然（例如 Forming & Baking 出事會影響下游 Fulfilment）。手機寬度時三欄退化為上下堆疊的三段，順序不變。

**Why this priority**: 這是「致敬 Argo CD」從狀態點升級成拓樸語言的關鍵，也是 design specificity 的主要來源；但它建立在既有卡片資料與分組之上，先有 US1、US2 已能交付可見的改版價值。故列 P2。

**Independent Test**: 以既有的 5 台固定機台與三個分組渲染主畫面，確認三欄順序、歸屬與連線正確；搜尋過濾後某欄為空時版面仍穩定；手機寬度下三段順序正確且無溢出。

**Acceptance Scenarios**:

1. **Given** 5 台機台皆有遙測，**When** 檢視桌機主畫面，**Then** 三個 stage 欄依 Prep → Forming & Baking → Fulfilment 由左至右排列，mixer-01 在第一欄，press-02 與 oven-04 在第二欄，pack-03 與 sorter-05 在第三欄，欄間有指向下游的連線。
2. **Given** 使用者搜尋只剩一台機台，**When** 其他欄位為空，**Then** 空欄以明確的空狀態呈現（不消失、不塌陷），連線語意仍成立；清除搜尋後版面回到原狀且無 layout shift。
3. **Given** 某台機台轉為 critical，**When** 觀察拓樸，**Then** 該卡片的狀態變化在不改變卡片尺寸與欄位寬度的前提下可辨。
4. **Given** 手機寬度（390），**When** 檢視主畫面，**Then** 三個 stage 以同一順序上下堆疊，每段有 stage 標題，卡片不溢出、不重疊。
5. **Given** 遙測以高頻抵達，**When** 拓樸持續更新，**Then** 畫面仍維持「每幀最多一次提交」的更新節奏，連線與卡片不逐筆重繪。
6. **Given** 下游 stage 的 throughput 明顯升高，**When** 觀察連線，**Then** 連線變粗且流動速度加快；throughput 降低時反向變化；兩套主題下流動效果皆可辨。
7. **Given** 使用者偏好減少動態效果，**When** 檢視連線，**Then** 連線仍隨 throughput 變粗細，但無沿線流動效果。

### User Story 4 - 診斷串流與結果的呈現（Priority: P2）

操作者按下 Diagnose 後，看到的不是 raw JSON 滾動，而是結果骨架（摘要、建議動作、可能原因、證據）隨著 AI 輸出逐步被填滿，游標停在正在生成的欄位上；原始串流文字仍可展開查看。完成後，結果依「先看該做什麼」的順序排列：摘要與嚴重度 → 建議動作 → 可能原因 → 證據（證據預設收合、同模式的紀錄合併）；完成態不再以滿版綠色進度條表達，而是一行產生時間與耗時，嚴重度以色條呈現。再次診斷命中快取時，耗時以大字與上一次非快取耗時並列，結果整塊直接出現，讓「秒回」本身被看見。

**Why this priority**: 串流與快取是 demo 的兩個情緒高點，critique 列為 P1；但它只動 drawer 內部，不影響其他面板，可在 US1／US2 之後獨立交付。故列 P2。

**Independent Test**: 對一台機台觸發診斷，觀察串流期間結果骨架逐步填入且原始串流可展開；完成後確認區段順序、證據收合與合併、完成 meta 與嚴重度色條；立即再診斷同一台，確認 Cached 的耗時對比呈現。失敗路徑確認 Retry 與中斷前推理仍保留。

**Acceptance Scenarios**:

1. **Given** 診斷進入 active 並開始收到 token，**When** 觀察 drawer，**Then** 摘要、可能原因、建議動作的區塊隨 token 抵達逐步出現內容，游標位於正在填入的欄位；「原始串流」可展開查看逐字文字。
2. **Given** token 尚不足以解析出任何欄位，**When** 觀察 drawer，**Then** 骨架以佔位狀態呈現，不顯示錯誤、不顯示空白。
3. **Given** 診斷完成且嚴重度為 Warning，**When** 檢視結果，**Then** 區段順序為摘要與嚴重度 → 建議動作 → 可能原因 → 證據；drawer 頂部以 warning 語意色條標示，不出現綠色滿版進度條；一行 meta 顯示完成時間與耗時。
4. **Given** 證據多於 2 筆且有多筆來源與模式相同的紀錄，**When** 檢視證據區，**Then** 預設只展開前 2 筆並顯示「還有 N 筆」的展開控制；同模式紀錄合併為一列並顯示次數與最近時間。
5. **Given** 對同一台、同一狀態再次診斷並命中快取，**When** 結果出現，**Then** 結果整塊直接呈現（不走逐字動畫），耗時以不小於遙測值的字級顯示，並與該台上一次非快取耗時並列；Cached 標記清楚可見。
6. **Given** 診斷失敗，**When** 檢視 drawer，**Then** 錯誤以人類可讀的分類說明（例如 worker 中斷、逾時、連線中斷）呈現，提供 Retry，並保留中斷前的推理內容。
7. **Given** 使用者偏好減少動態效果，**When** 串流進行中，**Then** 游標與填入動畫停止，內容仍逐步出現。

### User Story 5 - 異常與診斷狀態的記憶（Priority: P2）

值夜班的操作者低頭幾秒再抬頭，仍能知道剛才哪台出過事：機台回到 healthy 後，卡片在一段時間內保留「最近曾 critical／warning」的標記，直到時間過去或操作者確認；側欄有一列「最近異常摘要」列出目前異常與最近曾異常的機台（狀態燈、機台、相對時間，可點選台）；卡片顯示該台目前的診斷狀態（診斷中、有結果、快取、失敗），多台並行診斷時不必靠記憶；Event Stream 的每一列可點擊直接選取該機台；warning 卡片的邊框在任何主題下都清楚可辨。

**Why this priority**: critique 指出異常「在被看到之前就消失」是值夜班情境的核心缺口；全部可由前端自既有事件衍生，不需契約。它影響卡片、側欄與事件列三處，可在 US1 之後獨立交付。故列 P2。

**Independent Test**: 觀察一台機台經歷 healthy → critical → healthy，確認卡片在回復後保留標記達設定時間或至確認為止；側欄異常摘要列的狀態燈與最近異常時間正確、點擊可選台；對兩台並行診斷，卡片各自顯示正確的診斷狀態；點擊事件列選取對應機台。

**Acceptance Scenarios**:

1. **Given** 某台機台由 critical 回到 healthy，**When** 回復後的 30 秒內，**Then** 卡片仍帶有「最近 critical」的標記與相對時間（如「critical · 12 秒前」），30 秒後自動清除；標記不改變卡片尺寸。
1a. **Given** 卡片帶有異常標記，**When** 操作者點擊該標記（或側欄異常摘要列該台的清除動作），**Then** 卡片標記與摘要列該台同時清除；標記為可聚焦的按鈕、具可讀名稱，鍵盤 Enter 亦可清除。
2. **Given** 任一台機台處於 warning／critical 或最近曾異常，**When** 檢視側欄的異常摘要列，**Then** 該台出現在摘要列並顯示狀態燈、機台名稱與最近異常相對時間，點擊即選取該台；healthy 且無近期異常者不出現；全部正常時摘要列顯示明確的空狀態。
3. **Given** 兩台機台同時處於不同診斷狀態（一台診斷中、一台有快取結果），**When** 檢視卡片，**Then** 各卡片顯示各自的診斷狀態標記（診斷中含進度、有結果含嚴重度、快取、失敗），切換選取不影響其他卡片的標記。
4. **Given** Event Stream 有一筆 `Press 02 entered CRITICAL`，**When** 點擊該列，**Then** press-02 成為選取機台，Copilot 面板切到該台。
5. **Given** 同一台機台在 10 秒內反覆進入 warning，**When** 檢視 Event Stream，**Then** 重複事件合併為一列並顯示次數，新的 critical 事件不被洗掉。
6. **Given** 任一主題下有 warning 卡片，**When** 與 healthy 卡片並排，**Then** warning 卡片有可辨的邊框或色條，不再只靠幾乎不可見的內嵌環。

### User Story 6 - 響應式與平板策略（Priority: P3）

操作者在 768–1279 寬度的平板或窄桌機上使用監控台時，工具列的控制項不重疊、不裁切，搜尋在空間不足時收成圖示、點擊後展開；Copilot 面板在所有寬度下預設收合、選取機台後自動展開，主畫面拿到足夠的寬度；手機的 bottom-sheet 有抓取把手，閒置時不留大片空白。

**Why this priority**: 這是 critique 的 P2，且產品約束明文禁止 UI 重疊；但它是前面所有 story 的收尾整理，不帶新機制。故列 P3。

**Independent Test**: 於 1366×768、768×1024、390×844 三個 viewport 逐一截圖，確認工具列無重疊、搜尋收合與展開行為、面板預設狀態與 bottom-sheet 把手。

**Acceptance Scenarios**:

1. **Given** viewport 寬 1024，**When** 檢視工具列，**Then** 所有控制項完整可見且互不重疊，Diagnose 按鈕不被裁切。
2. **Given** 工具列空間不足以放下完整搜尋框，**When** 檢視工具列，**Then** 搜尋收成圖示按鈕，點擊後展開為可輸入的搜尋框，輸入完成或失焦後收回。
3. **Given** 任一 viewport 且未選取機台，**When** 頁面載入，**Then** Copilot 面板收合、主畫面佔滿可用寬度；選取機台後面板自動展開；使用者手動收合後，於同一台再按診斷或切換機台時重新展開，手動收合的偏好在重新載入後保留。
4. **Given** 手機寬度開啟 Copilot bottom-sheet，**When** 檢視 sheet，**Then** 頂部有抓取把手，閒置態內容不留超過一半高度的空白。
5. **Given** 手機寬度，**When** 頁面載入，**Then** 主畫面頂端有一條 Fleet Health 摘要列（比例條與 healthy／warning／critical／stale 四個計數）不捲動即可見；點擊摘要列展開異常摘要列（內容與桌機側欄相同、可點選台），再點收合；主題切換位於工具列。

### User Story 8 - 鍵盤操作與快捷鍵（Priority: P3）

熟練的操作者不用滑鼠也能完成主要流程：按 `/` 聚焦搜尋，輸入到只剩一台時按 Enter 即選取；在拓樸上用方向鍵在卡片間移動、Enter 選台、`d` 對選取機台觸發診斷、Escape 關閉 Copilot 面板或取消選取；按 `?` 顯示快捷鍵說明層。側欄寬度與事件列高度的拖曳把手也能以鍵盤調整。

**Why this priority**: critique 的「彈性與效率」與「說明」兩項各只得 1 分，是 SC-002（≥ 30/40）最難補的缺口；純前端、不影響其他 story 的版面，可最後交付。故列 P3。

**Independent Test**: 只用鍵盤完成「搜尋 → 選台 → 診斷 → 關閉面板 → 取消選取」整條流程；按 `?` 看到說明層並以 Escape 關閉；用鍵盤調整側欄寬度與事件列高度。

**Acceptance Scenarios**:

1. **Given** 焦點不在輸入欄，**When** 按 `/`，**Then** 搜尋框取得焦點；輸入使結果只剩一台後按 Enter，該台被選取且 Copilot 面板展開。
2. **Given** 焦點在拓樸的某張卡片，**When** 按方向鍵，**Then** 焦點依視覺位置移到相鄰卡片（跨 stage 欄亦可）；按 Enter 選取該台；按 `d` 對選取機台觸發診斷（與按 Diagnose 按鈕相同的前置條件與去重）。
3. **Given** Copilot 面板展開，**When** 按 Escape，**Then** 面板收合；再按一次 Escape 取消選取機台；任何寬度皆然。
4. **Given** 焦點不在輸入欄，**When** 按 `?`，**Then** 顯示快捷鍵說明層，列出全部快捷鍵，Escape 或再按 `?` 關閉；說明層不遮住工具列。
5. **Given** 焦點在側欄或事件列的拖曳把手，**When** 按方向鍵，**Then** 寬度或高度以固定步距調整，且把手有可讀名稱與目前值。
6. **Given** 焦點在輸入欄內，**When** 按 `/`、`d`、`?`，**Then** 視為一般輸入，不觸發快捷鍵。

### Edge Cases

- **主題偏好無法保存**（隱私模式、儲存被封鎖）：每次載入回到預設淺色，切換仍可用，不顯示錯誤。
- **系統偏好為深色但使用者未曾切換**：仍以淺色呈現（light 為預設，不跟隨系統），切換後以使用者選擇為準。
- **串流內容不是合法 JSON 或在中途截斷**：結果骨架維持已解析的部分，未解析部分保持佔位；完成或失敗後以原始串流為準呈現，不顯示解析錯誤給操作者。
- **串流在 token 尚未抵達時即完成（快取命中）**：直接呈現完整結果與耗時對比，不出現骨架填入動畫。
- **多台同時 critical**：拓樸同時標示多張卡片，連線語意不變；脈動類動效不疊加成整面閃爍。
- **搜尋使某個 stage 欄完全為空**：欄位保留並顯示空狀態，順序與寬度不變。
- **latch 期間機台再次異常**：以最新一次異常重置計時與標記，不產生重複標記。
- **Event Stream 達 50 筆上限**：合併與可點擊行為不變，最舊的先移除。
- **斷線期間**：既有「保留最後資料並標 stale」的語意不變；背壓 strip 停止累積並標示連線中斷；主題切換仍可用。
- **使用者偏好減少動態效果**：走勢線改為靜態重繪、串流游標與填入動畫停止、拓樸連線退回只變粗細、無流動效果；狀態仍由顏色、文字與輔助技術名稱傳達。
- **使用輸入法組字中按 Enter**：搜尋框內的 Enter 若屬輸入法選字（composition 中）MUST NOT 觸發選取，只有組字結束後的 Enter 才選取。
- **視窗在主題切換瞬間被縮放**：版面與主題各自獨立完成，不互相阻塞。
- **手機上摘要列展開時**：異常摘要列以覆蓋層呈現、不推擠下方的拓樸三段；Escape 或點擊外部收合。
- **1366×768 常見筆電**：三欄拓樸與 Copilot 面板同時展開時主畫面每欄至少容納一張完整卡片，不出現橫向捲動。

## Requirements *(mandatory)*

### Functional Requirements

**視覺世界與主題（US1）**

- **FR-001**: 系統 MUST 提供淺色與深色兩套完整主題，淺色為首次載入的預設；兩套主題共用同一組語意化的設計 token 名稱，只有值不同。
- **FR-002**: 使用者 MUST 能在介面上以單一控制項切換主題；切換 MUST 在同一幀內完成，不得出現白屏、閃爍或版面位移。
- **FR-003**: 系統 MUST 在本機保存使用者的主題選擇並於下次載入套用；無法保存時 MUST 回到預設且不顯示錯誤。
- **FR-004**: 所有機台狀態（healthy／warning／critical／stale）與連線狀態（connected／reconnecting／disconnected／unauthorized）在兩套主題下 MUST 同時具備顏色、文字標籤與輔助技術可讀名稱；同一狀態在所有面板 MUST 使用同一組語意色。
- **FR-005**: 兩套主題下所有功能性文字對其底色的對比 MUST ≥ 4.5:1；功能性文字（徽章、單位、計數、時間戳）MUST NOT 小於 11px。
- **FR-006**: 新視覺世界 MUST 遵守既有產品約束：首屏為可操作監控台、卡片圓角不超過 8px、不使用大面積紫色漸層／裝飾光球／bokeh、不使用 Argo CD 官方 logo／商標／品牌配色。
- **FR-007**: 顏色、圓角、陰影、間距 MUST 一律使用具名 token，MUST NOT 在元件內散落硬編碼色值。
- **FR-008**: 介面字型堆疊 MUST 含 CJK 字族，使中英混排的基線與字距一致；機器產生的值（id、數值、時間、串流原文）維持等寬字型。

**背壓常駐可見（US2）**

- **FR-009**: 系統 MUST 在首屏常駐顯示每秒收到的遙測訊息數、每秒渲染批次數與兩者比值；在四個驗收 viewport 下 MUST 不捲動、不收合任何面板即可見；任何斷點 MUST NOT 整體隱藏它，手機寬度至少保留比值數字。
- **FR-010**: 背壓區 MUST 含一條最近 60 秒的走勢線，同時呈現訊息速率與渲染速率。
- **FR-011**: 因背壓丟棄的訊息數大於 0 時 MUST 以警示語意色顯示於同一區域；為 0 時不佔版面。
- **FR-012**: 背壓區的更新 MUST 走既有的 buffer 與每幀批次提交節奏，MUST NOT 逐筆寫入畫面狀態。

**產線 stage 拓樸（US3）**

- **FR-013**: 主畫面 MUST 以三個 stage 欄呈現機台，順序固定為 Prep → Forming & Baking → Fulfilment，機台歸屬依既有的跨端單一分組來源；側欄 MUST 只含品牌列、Fleet Health、最近異常摘要列（FR-027）與主題切換，不再重複機台清單。
- **FR-014**: 相鄰 stage 之間 MUST 有指向下游的連線；連線的粗細 MUST 隨下游 stage 的 throughput 遙測變化，並帶有沿線流動的動效，流速與 throughput 掛鉤；連線 MUST 在兩套主題下可辨。使用者偏好減少動態效果時 MUST 退回「只變粗細、無流動」；throughput 來源為既有遙測欄位，不新增契約。（clarify 2026-10-15：使用者選定 C「粗細加流動動畫」）
- **FR-015**: 搜尋過濾後任一 stage 為空時，該欄 MUST 保留並顯示空狀態，欄寬與順序 MUST 不變；清除過濾後 MUST NOT 產生 layout shift。
- **FR-016**: 手機寬度時三個 stage MUST 以同一順序上下堆疊，每段帶 stage 標題。
- **FR-017**: 拓樸的狀態變化（含 critical 脈動）MUST NOT 改變卡片尺寸或欄位寬度。

**診斷串流與結果（US4）**

- **FR-018**: 串流期間系統 MUST 以容錯方式漸進解析 AI 輸出，並把已解析的摘要、可能原因、建議動作逐步填入與完成態相同的結果骨架；尚未解析出的欄位 MUST 以佔位呈現；解析失敗 MUST NOT 對操作者顯示錯誤。
- **FR-019**: 原始串流文字 MUST 仍可由操作者展開查看。
- **FR-020**: 完成態結果區段順序 MUST 為：摘要與嚴重度 → 建議動作 → 可能原因 → 證據。
- **FR-021**: 證據 MUST 預設只展開前 2 筆並提供展開其餘的控制；來源與模式相同的多筆紀錄 MUST 合併為一列並顯示次數與最近時間。
- **FR-022**: 完成態 MUST 以一行 meta 顯示完成時間與耗時，並以嚴重度語意色條標示；MUST NOT 以滿版 ok 色進度條表達完成。
- **FR-023**: 快取命中時 MUST 顯示本次耗時，並與該台上一次非快取耗時並列對比；結果 MUST 整塊直接呈現，不走逐字動畫；Cached 標記 MUST 清楚可見。耗時由前端自送出請求至收到完成事件量測。
- **FR-024**: 失敗態 MUST 以人類可讀的分類說明錯誤、提供 Retry，並保留中斷前的推理內容；既有的 45 秒無進展收尾語意不變。
- **FR-025**: 既有的每機台診斷狀態機（idle／active／completed／failed、多台並存、active 期間同台不得重複送出、中止診斷）MUST 維持不變。

**異常與診斷狀態的記憶（US5）**

- **FR-026**: 機台由 warning／critical 回到 healthy 後，卡片 MUST 保留「最近異常」標記與相對時間達 30 秒，或至操作者清除為止；清除動作 MUST 同時存在於卡片標記本身（可點擊、可聚焦、具可讀名稱）與側欄異常摘要列的該台列，兩處操作同一份狀態；期間再次異常 MUST 重置計時並恢復標記；標記 MUST NOT 改變卡片尺寸。
- **FR-027**: 側欄 MUST 提供「最近異常摘要列」：列出目前處於 warning／critical 與最近 30 秒內曾異常的機台，每列含狀態燈、機台名稱、最近異常相對時間，可點擊選取該台；全部正常時顯示空狀態。側欄 MUST NOT 再列出完整機台清單（拓樸三欄已承載）。
- **FR-028**: 卡片 MUST 顯示該台目前的診斷狀態標記（診斷中含進度、有結果含嚴重度、快取、失敗、無）；標記由既有的每機台診斷狀態衍生。
- **FR-029**: Event Stream 的每一列 MUST 可點擊以選取對應機台；10 秒內同一機台的重複事件 MUST 合併為一列並顯示次數；上限 50 筆的語意不變。
- **FR-030**: warning 卡片 MUST 以可辨的邊框或色條區別於 healthy 卡片，兩套主題皆然。

**響應式（US6）**

- **FR-031**: 於 1366×768、1440×900、768×1024、390×844 四個 viewport，兩套主題下 MUST 無文字溢出、無控制項重疊或裁切、無橫向捲動、hover／selected／pulse 不造成 layout shift。
- **FR-032**: 工具列空間不足時搜尋 MUST 收成圖示按鈕並可展開輸入；MUST NOT 以壓縮搜尋框的方式讓鄰近控制項重疊。
- **FR-033**: Copilot 面板在所有 viewport MUST 預設收合，選取機台後 MUST 自動展開；使用者 MUST 能手動收合，手動收合偏好 MUST 保存在本機並於下次載入套用（但選取新機台或觸發診斷時 MUST 展開）；手機 bottom-sheet MUST 有抓取把手。
- **FR-033a**: 手機寬度（側欄隱藏）時，Fleet Health MUST 以主畫面頂端一條常駐摘要列呈現（比例條與四個計數），點擊 MUST 展開為異常摘要列（與 FR-027 同一份資料與行為），再點收合；主題切換 MUST 移入工具列的系統狀態分組。
- **FR-034**: 工具列 MUST 以語意分組呈現控制項（導航／播放控制／系統狀態／主要動作），任一分組的可見選項 MUST NOT 超過 4 個。

**鍵盤操作（US8）**

- **FR-034a**: 系統 MUST 提供快捷鍵：`/` 聚焦搜尋、搜尋結果只剩一台時 Enter 選取、方向鍵在拓樸卡片間依視覺位置移動焦點、Enter 選取聚焦的卡片、`d` 對選取機台觸發診斷（前置條件與去重同 Diagnose 按鈕）、Escape 依序收合 Copilot 面板與取消選取；焦點位於輸入欄時字母與符號快捷鍵 MUST NOT 觸發。
- **FR-034b**: 系統 MUST 提供以 `?` 開關的快捷鍵說明層，列出全部快捷鍵，可用 Escape 關閉，且不遮住工具列。
- **FR-034c**: 側欄寬度與事件列高度的拖曳把手 MUST 可用鍵盤以固定步距調整，並具備可讀名稱與目前值。
- **FR-034d**: 每張拓樸卡片 MUST 只佔一個 Tab 停駐點；卡片上的診斷圖示按鈕 MUST 在卡片取得焦點時可見並可達，但不另佔 Tab 停駐點（以 `d` 或 Enter 後的面板操作觸發）。

**真實來源與文件（US7）**

- **FR-035**: 合併前 MUST 把憲章「視覺」條目改為指向 `apps/web/PRODUCT.md` 與 `apps/web/DESIGN.md`（經 `/speckit-constitution` 修訂），並同步 CLAUDE.md 真實來源段、README 設計連結、指南 §15.6、CHANGELOG `[Unreleased]`。
- **FR-036**: `apps/web/design/design-spec.md` MUST 標示為歷史文件並指向現況；`apps/web/design/refs/*.png` MUST 自 repo 移除。
- **FR-037**: `apps/web/DESIGN.md` 與其 sidecar MUST 於改版完成後重新產出，反映實際落地的兩套主題 token 與元件，作為後續 feature 的視覺真實來源。

### Key Entities

- **主題偏好（Theme Preference）**：使用者選擇的主題（light／dark），保存在本機；預設 light；不隨系統偏好自動變更。
- **面板偏好（Panel Preference）**：Copilot 面板的手動收合狀態，保存在本機；預設收合，選取機台或觸發診斷時展開。
- **背壓指標（Backpressure Metrics）**：由既有計數衍生的每秒訊息數、每秒批次數、比值、丟棄數，以及最近 60 秒的兩條速率序列；前端衍生，不新增契約欄位。
- **Stage**：產線階段（Prep／Forming & Baking／Fulfilment），有固定順序與所屬機台集合，來源為既有的跨端分組。
- **Stage 連線（Flow Link）**：相鄰 stage 之間的下游連線，粗細與流速由下游 stage 各機台 throughput 的彙總衍生（每幀批次更新）；減少動態效果時只保留粗細。
- **異常標記（Anomaly Latch）**：每台機台最近一次 warning／critical 的時間與等級、回復時間、清除期限（30 秒）與「已由操作者清除」旗標；單一狀態來源，卡片標記與側欄異常摘要列同時讀寫；由既有遙測狀態轉換前端衍生。
- **診斷狀態標記（Diagnosis Badge）**：每台機台的診斷狀態摘要（診斷中與進度、完成與嚴重度、快取、失敗、無），由既有每機台診斷狀態衍生。
- **診斷耗時（Diagnosis Timing）**：每台機台最近一次非快取診斷的耗時與最近一次快取命中的耗時，前端量測。
- **漸進解析結果（Partial Result）**：串流進行中已解析出的欄位集合與各欄位的「生成中／已完成」狀態。

## Assumptions

- **light 為預設且不跟隨系統偏好**：首次載入一律淺色，即使作業系統偏好深色；使用者切換後以本機保存的選擇為準。理由：使用者裁決「light 為預設、dark 為次要」，跟隨系統會讓預設在不同機器上不一致，不利 demo。
- **主題切換控制項放在側欄**（與 Fleet Health 同區，手機時移入工具列的系統狀態分組）；不做自動排程切換。
- **異常標記保留 30 秒**，可由操作者在卡片標記或側欄異常摘要列清除；30 秒取自 critique 建議。
- **證據預設展開 2 筆**、同來源同模式合併；「模式」指狀態轉換對（如 healthy → critical）相同者。
- **Cached 的耗時對比**以「該台上一次非快取診斷」為基準；若本次 session 內尚無非快取紀錄，只顯示本次耗時。
- **拓樸連線為前端靜態結構**，依 stage 順序繪製，不消費任何「流量」資料（契約中沒有）；FR-014 的 clarification 只決定連線是否以既有 throughput 遙測做視覺化。
- **既有 mock Hz 控制維持 disabled 占位**（後端無對應能力），改版可改其呈現但不賦予功能。
- **README 截圖**：013 範圍內重拍全部 12 張功能截圖（以 light 主題為主），另加 1 張 dark 主題與 1 張 stage 拓樸全景，共 14 張；以可重播的截圖劇本產出（沿用本次 critique 的截圖腳本）。demo 影片是否重錄留待 release 步驟決定（PRODUCT.md 已列為未決）。（clarify 2026-10-15：使用者選定 A）
- **impeccable 工作流在 plan 與 implement 階段使用**：plan 階段以 `/impeccable shape` 選定視覺世界並產出 direction contract；implement 階段的 UI 編輯遵守其 craft floor；收尾以 finish-reviewer 審、documenter 重寫 DESIGN.md。這些是開發方法，不是產品需求。
- **依賴**：既有 `apps/web/PRODUCT.md`（產品事實）、`apps/web/DESIGN.md`（1.1.0 舊視覺紀錄，作反面參考）、critique 快照、既有的 12 則 WS 訊息與 `POST /diagnoses`、既有的機台分組單一來源。
- **不在範圍**：契約與後端任何變更；mock Hz 真正作用；診斷結果讀取端點與重連 rebind（roadmap 012-lite）；Prometheus／Grafana 類儀表板；多語系切換機制（文案已裁決為單一繁體中文）。
